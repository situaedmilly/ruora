## §4 INVARIANTS

**INV-SOR-1 — IDENTITY/STATE SPLIT.** No field inside an immutable version's
bytes may be required to change for the object to lawfully change state or
standing. If it must change, it was never identity — it was state wearing
identity's clothes.

**INV-SOR-2 — STATE IS RELATIONAL.** Every living predicate over an object is
a governed relation (`StateOf(version, predicate, authority, valid_time)`),
never a property of the version. ACTIVE, CONSTITUTED, CONSUMED, ADMITTED,
CANONICAL are relation names, not field values.

**INV-SOR-3 — NON-CONTAINMENT.** An object never contains the ledger about
it. Any serialization that packages identity together with its state relations
as one identity-bearing artifact is a defect of this class, regardless of
schema elegance.

**INV-SOR-4 — INTRINSIC STATE TEXT IS DECLARATION-CLASS.** A version's bytes
may DESCRIBE an expected or authoring-time state (as M5's bytes described
DRAFT; as this artifact's §0 describes CANDIDATE). Such text is a claim
carrying declaration class only. It never establishes, blocks, or contradicts
the ledger. This dissolves the ACTIVE/DRAFT contradiction class: the bytes say
what the author believed at freeze; the ledger says what is true.

**INV-SOR-5 — BITEMPORALITY.** Every state relation carries VALID_TIME (when
the state holds in governed reality) and RECORD_TIME (when the estate learned
and recorded it), distinctly. Corrections append (`StandingRevision`,
disposition `DEFEATED`, with effective scope); history is never rewritten. The
system must remain able to answer both: *what did we believe at t?* and *what
currently governs our interpretation of t?*

**INV-SOR-6 — HISTORY ≠ MEMORY ≠ CURRENT STANDING.** History is what records
occurred (immutable). Memory is which prior records are made available to
future computation (governed selection). Current standing is what those
records are presently allowed to support (adjudicated). Stale memory may never
silently govern. Same law as `CONVERSATION_MEMORY != GOVERNING_MEMORY`, one
scale up.

**INV-SOR-7 — RELATION LIFECYCLE BY APPEND.** Relations end by supersession,
revocation, or expiry records — never by deletion or in-place edit. A relation
record is itself version-frozen once written; its own fate is later records
about it. The recursion is safe because it is append-only.

**INV-SOR-8 — AUTHORITY DOES NOT COMPOSE FOR FREE.**
`Authorized(f) ∧ Authorized(g)` does NOT imply `Authorized(g∘f)` — scopes may
not compose. Composability of authority is its own mathematical object and
requires its own grant law (OQ-SOR-4).

**INV-SOR-9 — WRITER AUTHORITY PER RELATION CLASS.** Every ledger record class
names which authority class may append it, declared by the admission/issuing
side, never self-declared by the writer. (This generalizes Round-3 T1-M1's
`write_set` gap from files to relations.) Where the grants are unissued, the
gap is disclosed on every affected record — never defaulted.

**INV-SOR-10 — IDENTITY CONTINUITY IS WITNESSED INVARIANT PRESERVATION.**
Continuity of a SELF or any governed object across version, state, projection,
substrate, memory, role, and authority change is established only by witnessed
preservation of its declared identity_invariants. Name equality establishes
nothing. Memory continuity alone establishes nothing. Substrate persistence
establishes nothing.

**INV-SOR-11 — PROOF-SCOPE DISCIPLINE.** Every measurement carries its
supported proposition AND its unsupported propositions. A digest proves byte
equality, not truth. A remote surface returning bytes proves resolvability for
that receiver at that time, not universal resolvability. (Inherited from the
estate's metrology; made foundational here.)

**INV-SOR-12 — PROJECTION LAW.** `MODEL != SELF != PROJECTION != SUBSTRATE`.
A projection is a time-scoped relation from an identity to a substrate, role,
and chamber. A SELF survives state change because state is not identity; loses
authority without ceasing to be SELF; carries stale memory without losing
identity; is projected into a chamber without becoming the chamber. These are
now derivations of INV-SOR-1/2/10, not slogans.

**INV-SOR-13 — SINGLE-USE BY UNIQUENESS.** Single-use is a ledger uniqueness
constraint (at most one consumption record per identity), never a mutable
field inside the consumable. A second consumption record is the detectable
breach event; the consumable's bytes never change.
