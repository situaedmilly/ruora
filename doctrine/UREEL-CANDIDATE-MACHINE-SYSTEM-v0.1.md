# UREEL Candidate Machine System v0.1

## 1. Prime thesis

The UREEL candidate machine system exists to manifest a worker body capable of carrying Unreal pressure while remaining subordinate to RUORA proof law. Hardware power alone does not qualify a candidate.

This doctrine defines the system by which a real worker candidate is manifested, classified, evaluated, bounded, and either accepted or rejected before UNREAL-002 can be authorized.

It does not identify an actual candidate.

It does not authorize implementation.

## 2. Reverse-engineered chain

```text
Reality Engine Output
↓
UREEL Unreal Proof Chamber
↓
Worker Machine Capability
↓
Access + Storage + Rollback Boundary
↓
Secretless Git/Artifact Flow
↓
Human_TURN Authorization
↓
Candidate Evaluation
↓
Machine Requirements
↓
Candidate Manifestation
```

The chain is read from desired output backward to the governed conditions required before a machine may enter evaluation.

Candidate manifestation is the presentation of a real machine with verifiable facts. It is not purchase, rental, provisioning, installation, access configuration, or execution.

## 3. System identities

- RUORA = authority, doctrine, and proof body.
- Mac mini = command console, not worker.
- UREEL = worker execution identity.
- Candidate Machine = physical or rented body proposed to carry UREEL.
- Unreal = pressure load.
- Artifacts = candidate evidence only.
- Human_TURN = authorization gate.
- UNREAL-002 = implementation authorization gate.

These identities must remain distinct.

The Candidate Machine does not inherit authority from UREEL's name. UREEL does not inherit authorization from candidate capability. Artifacts do not become proof until Human_TURN reviews and seals them through RUORA.

## 4. Governed system layers

| Layer | Question | Required truth |
| --- | --- | --- |
| Identity | What is this machine called? | UREEL |
| Body | What machine physically carries UREEL? | Pending |
| Capability | Can it run Unreal properly? | Windows + RTX-class GPU + 32 GB RAM + 1 TB NVMe |
| Access | How do we enter it? | Local login or authorized remote desktop |
| Storage | Where does Unreal live? | Isolated worker path |
| Git | Does it write to RUORA? | Not unless separately authorized |
| Secrets | Can it hold credentials? | No production secrets |
| Artifacts | What does it return? | Screenshots, logs, README, and render proof candidates |
| Rollback | Can it be erased safely? | Must be reversible |
| Authority | Can it authorize itself? | Never |

The capability row is a requirement floor, not a claim about an existing candidate.

- RTX-class discrete GPU or equivalent
- 32 GB RAM minimum
- 1 TB NVMe SSD minimum
- direct Human_TURN accountable access

Fast access without immediate hardware purchase.

- 32 GB RAM minimum

## 6. Qualification outcomes

Candidate evaluation must assign exactly one of these three outcomes:

### QUALIFIED

The candidate satisfies the minimum floor and all access, secret, Git, and rollback boundaries.

### CONDITIONALLY_QUALIFIED

The candidate satisfies the capability floor but has unresolved access, storage, rollback, billing, or security conditions.

This outcome does not authorize implementation. Every unresolved condition must be recorded and cleared before Human_TURN may consider UNREAL-002 authorization.

### REJECTED

The candidate fails the required capability floor, violates governance boundaries, or cannot produce verifiable facts.

Rejection applies to the evaluated candidate facts only. It does not alter sealed RUORA authority or authorize a replacement candidate by assumption.

## 8. No-invention rule

Codex may classify and evaluate candidate facts, but Codex may not invent candidate facts.

Candidate identity, ownership, rental status, access, operating system, GPU, RAM, CPU, storage, paths, rollback, billing, security, and evidence remain unknown until Human_TURN provides verifiable facts.

No class baseline may be copied into a candidate packet and represented as an observed machine fact.

## 9. No-implementation rule

Candidate system doctrine does not authorize Unreal installation, project creation, remote access setup, hardware purchase, UWebBrowser implementation, Pixel Streaming, deployment, Git write access, secret transfer, or worker execution.

It also does not authorize cloud provisioning, package installation, API calls, Bubble mutation, schema mutation, app implementation, remote creation, push, worktree creation, or PR creation.

UNREAL-002 remains incomplete and MANUAL_REQUIRED.

Implementation remains blocked.

## 10. Evaluation flow

1. Human_TURN provides candidate fact packet.
2. Codex checks packet completeness.
3. Codex compares facts against sealed requirements.
4. Codex assigns one outcome: QUALIFIED, CONDITIONALLY_QUALIFIED, or REJECTED.
5. Repo records evaluation doctrine.
6. Human_TURN decides whether to authorize UNREAL-002.
7. Implementation remains blocked until explicit Human_TURN authorization.

Evaluation records judgment against supplied evidence. They do not create missing evidence, authorize the machine, or authorize implementation.

## 11. Access, storage, and rollback boundary

- Access must be direct local login or separately authorized remote desktop access.
- Shared or unaccountable access does not qualify.
- Unreal installation and project paths must be isolated from RUORA root doctrine.
- Storage must satisfy the sealed capability floor and preserve artifact custody.
- Rollback must identify files, generated artifacts, worker-local state, installed software, accounts touched, and restoration steps.
- A candidate without a verifiable rollback proposal cannot be fully qualified.

No access method is authorized by this doctrine.

No install or project path is created by this doctrine.

## 12. Secretless Git and artifact boundary

- No production secrets may enter candidate files, screenshots, logs, configuration, assets, or packaged output.
- No service-role keys, API tokens, deployment keys, cloud credentials, or production credentials are authorized.
- No candidate receives Git write, remote push, production branch, PR, deployment, or doctrine authority.
- Candidate output returns to Local Mac and RUORA review as candidate evidence only.
- Reviewable artifacts may include screenshots, render stills, local video captures, implementation README files, verification transcripts, diffs, local build logs, and risk reports.

Repo remains proof body.

Worker builds do not govern.

## 13. Evidence law

A machine is not a candidate because it is imagined, desired, affordable, powerful, or available. It becomes a candidate only when Human_TURN provides verifiable facts for evaluation.

Availability is not qualification.

Capability is not authority.

Worker output is candidate evidence, not sealed proof.
