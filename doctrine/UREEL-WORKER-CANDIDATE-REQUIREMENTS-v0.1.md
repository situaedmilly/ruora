## 3. Candidate topology baseline

Selected topology family:

Dedicated Windows workstation or Shadow/Parsec-style remote workstation, with Local Mac remaining command console.

Required interpretation:

- Local Mac remains command console.
- UREEL carries Unreal pressure only after implementation is separately authorized.
- Worker output remains candidate evidence until Human_TURN review and seal.
- External SSD is storage relief only.
- Cloud GPU / EC2 remains deferred.
- Raspberry Pi / Compute Module remains rejected.

This is the candidate lane, not the selected machine.

## 4. Minimum acceptable hardware specs

The worker candidate must satisfy the following minimum acceptable specs:

- Operating system: Windows 11 Pro or later
- GPU class: discrete NVIDIA RTX-class GPU or equivalent
- GPU memory: 8 GB VRAM minimum, 12 GB preferred
- RAM: 32 GB minimum, 64 GB preferred
- CPU class: modern 8-core desktop CPU minimum, 12-core preferred
- Storage: 1 TB NVMe SSD minimum, 2 TB preferred
- Expandability: enough headroom for Unreal project source, derived data cache, build artifacts, and screenshot/render exports
- Thermal class: sustained workstation load without immediate throttling

The machine must be able to carry Unreal editor, compile, packaging, and simulation pressure without collapsing the command console into the render factory.

External SSD may help storage pressure, but it does not replace the required internal spec floor.

## 5. Access and ownership requirements

The candidate must have:

- ownership status: dedicated owned or dedicated rented single-tenant only
- location status: local physical workstation or dedicated remote workstation
- access method: direct local login or explicitly authorized remote desktop access
- session control: Human_TURN accountable access only
- shared access: not acceptable

The candidate must not be a shared lab machine, an ungoverned public box, or a casual family computer.

The candidate must not permit hidden account drift.

The candidate must not permit uncontrolled remote administration.

## 6. Unreal install and project requirements

The candidate must support:

- Unreal install location: dedicated non-system volume or isolated workspace path
- Unreal project location: isolated workspace path, not a disposable temp folder
- project shell isolation: future project shell must be separate from RUORA root doctrine
- artifact custody: build outputs must be capturable and reviewable

Recommended future path:

```text
projects/ureel-unreal-proof-chamber/
```

This file does not create that path.

No project shell is created by this doctrine.

No Unreal version is selected by this doctrine.

No plugin, asset, package, or bridge placeholder is created by this doctrine.

## 7. Rollback path requirements

Before any implementation incision, the candidate setup must have a rollback path.

Rollback must identify:

- files to remove
- generated artifacts to discard
- worker-local state to clean
- software installed or modified
- accounts touched, if any
- repo status before and after cleanup
- the commands needed to return the machine to its prior state

If rollback cannot be described, the candidate is not acceptable.

## 8. Secret boundary requirements

The candidate must satisfy the no-secret law:

1. No production secrets in Unreal files.
2. No service-role keys in project files.
3. No API tokens in Blueprints.
4. No credentials in screenshots, logs, config, assets, or packaged builds.
5. No remote worker receives secrets without separate Human_TURN authorization.
6. No browser projection may expose raw credentials.
7. No deployment keys are authorized.
8. No cloud credentials are authorized.

Machine facts do not authorize implementation.

Secret access remains blocked until a separate authorization exists.

## 9. Git boundary requirements

The candidate must satisfy the Git boundary:

- no remote push authority
- no production branch authority
- no unreviewed write access
- no automatic deployment path
- candidate output returns to Local Mac / repo review as evidence

Repo remains proof body.

Worker builds do not govern.

## 10. Evidence boundary requirements

The candidate must be able to produce reviewable evidence such as:

- screenshot
- render still
- local video capture
- implementation README
- verification transcript
- git diff
- local build log
- risk report

Worker output is candidate evidence, not proof, until reviewed and sealed by Human_TURN.
